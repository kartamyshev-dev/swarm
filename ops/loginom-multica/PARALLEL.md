# Восемь независимых потоков

Один проект и один сквад сохраняются. Генератор допускает один запуск, исполнитель и Ловец — по восемь на разных карточках. Карточки назначаются вручную; дополнительного диспетчера нет. Каждая карточка имеет свои checkout, ветку, пару аккаунтов Loginom, браузеры, CLI-состояние, пакеты и доказательства. Восемь отдельных авторизаций ChatGPT ограничивают число одновременных модельных прогонов Loginom CLI: свободную выбирает обвязка, девятый ждёт освобождения.

Используется существующий клиент с обычным обновлением OAuth-токенов. Изменения клиента, `shared-oauth-v1`, SSH, дополнительные контейнеры и новые стенды для этой схемы не нужны. Авторизация native агента Multica, авторизация модели Loginom CLI и аккаунты сервера Loginom — отдельные слои; постоянный пул относится к модели Loginom CLI.

## Сохранить старую работу и остановить возобновления

Перед установкой сохранить опубликованные SHA/PR, вложения и незавершённые изменения старых LGD/XLSX в приватном архиве вне managed root. Старые попытки не переписывать; неизвестные серверные эффекты сохранять для сверки. Отключить запускающие работу wakeups, отменить незавершённые карточки и **каждый активный запуск отдельно** через штатный API. Изменение статуса карточки само по себе не останавливает её процесс. После cancellation API подтвердить остановку технических процессов; до этого новую очистку тех же аккаунтов не запускать.

На время обслуживания не создавать новые задания, упоминания и расписания. Снимок API проверяет состояние, но не запрещает новые назначения. Установка выполняется одной явно назначенной служебной задачей Multica. В её приватном deployment указать `maintenance_issue_id`. Исключение idle-проверки допускает только один running запуск: точные `MULTICA_TASK_ID`, `MULTICA_AGENT_ID` и workspace из native окружения должны совпасть с API, а карточка — с `maintenance_issue_id` и текущим назначением служебному агенту. Другой активный/queued/неизвестный запуск запрещает установку. После обслуживания удалить `maintenance_issue_id`; общего переключателя «игнорировать задачи» нет.

## Установить проверенный bundle

Изолированная рабочая копия обвязки сохраняет чужие изменения. Bundle экспортируется из зафиксированного коммита `swarm`:

```sh
python3 ops/loginom-multica/scripts/package.py \
  --repo /path/to/swarm --ref <commit> --out /new/operator-bundle
```

Служебная задача получает только bundle штатными средствами Multica и устанавливает его проверенным helper:

```sh
PYTHONDONTWRITEBYTECODE=1 python3 <абсолютный-bundle>/scripts/install-bundle.py \
  --bundle <абсолютный-bundle> --commit <полный-commit-SHA> --digest <bundle-SHA256> \
  --deployment "$HOME/.config/loginom-multica/deployment.json"
```

Helper сверяет точный commit/digest, VERSION inventory и каждый файл, отвергает лишние файлы, ссылки и выход за границы. Новая копия готовится в приватном sibling staging и повторно проверяется; непосредственно перед переключением проверяется отсутствие других запусков. После переключения перечитываются VERSION и все хэши. Прежняя проверенная копия сохраняется целиком в приватном sibling checkpoint вне GC; чужие каталоги и неподтверждённые версии не удаляются. Обычная ошибка второго rename восстанавливает прежнюю копию. Два rename не являются одной транзакцией при SIGKILL/потере питания: тогда продолжение требует сверки сохранённого checkpoint. Активная копия обвязки одна. Полный Swarm не переносится. Не смешивать новые скрипты со старой ведомостью. Для служебных Python-команд задавать PYTHONDONTWRITEBYTECODE=1, чтобы generated caches не меняли inventory экспортированного bundle. Клиент для входа берётся из уже проверенной сборки существующего Loginom CLI; CLI manifest и полная целостность подтверждаются перед использованием.

## Один раз авторизовать восемь аккаунтов

Постоянные профили располагаются в `~/.config/loginom-multica/provider-accounts/01..08/profile`. Каталоги имеют права 0700, файл `data/auth.json` — 0600. Они находятся вне рабочих каталогов карточек и native GC. Профили хранят только авторизацию; история модели и состояние Loginom создаются заново внутри каждой попытки.

Служебная задача подготавливает профили и запускает штатный headless-вход существующего Loginom CLI:

```sh
python3 ~/.local/share/loginom-multica/scripts/prepare-provider-accounts.py prepare \
  --deployment "$HOME/.config/loginom-multica/deployment.json" \
  --cli <абсолютный-путь-проверенного-loginom-ai-agent-cli>

python3 ~/.local/share/loginom-multica/scripts/prepare-provider-accounts.py login \
  --deployment "$HOME/.config/loginom-multica/deployment.json" \
  --cli <абсолютный-путь-проверенного-loginom-ai-agent-cli> --slot 1 --timeout 900
```

Владелец открывает выданную ссылку и вводит код в браузере, затем повторяет для `--slot 2` … `--slot 8`, каждый раз выбирая **другой ChatGPT-аккаунт**. Токены записываются непосредственно на runtime; содержимое auth.json не пересылается в чат и не публикуется во вложениях. Вход и последующее использование одного файла защищаются одной постоянной блокировкой. CLI-профиль Codex для этого не подходит: формат авторизации Loginom CLI отличается.

После восьми входов проверить каталог и активировать пути:

```sh
python3 ~/.local/share/loginom-multica/scripts/prepare-provider-accounts.py check \
  --deployment "$HOME/.config/loginom-multica/deployment.json"

python3 ~/.local/share/loginom-multica/scripts/prepare-provider-accounts.py activate \
  --deployment "$HOME/.config/loginom-multica/deployment.json" \
  --operator "$HOME/.config/loginom-multica/operator.json" \
  --cards "$HOME/.config/loginom-multica/cards"
```

При нестандартном каталоге один абсолютный `--root` задаётся одинаково всем командам. Проверки отказываются принимать одинаковые пути/файлы, символические и жёсткие ссылки, неправильные права и копии одной авторизации. Конфигурация оператора и ролей получает список `provider_auth_files` из восьми абсолютных путей; конфиги Loginom-аккаунтов и их пароли сохраняются. Файлы токенов не копируются в рабочие каталоги. Старый одиночный `provider_auth_file` не используется новыми карточками.

## Подключение авторизации к попытке

Обвязка проверяет доступные файлы и пытается захватить существующий `auth.json.lock` без блокирующего системного ожидания. При занятых слотах ждёт ограниченное время с возможностью отмены; это ожидание входит в срок модельного запуска. Захваченный аккаунт фиксируется на попытку до её завершения и обработки журналов. Блокировка наследуется дочерними процессами, повторного захвата в launcher нет. Отмена родителя не освобождает ресурс ещё работающего ребёнка.

Для каждой попытки создаётся новый CLI-профиль. В него writable file bind подключается **только выбранный** постоянный auth.json. Обычное обновление токенов клиентом записывается в этот файл и доступно следующей попытке без нового входа. Токены до и после обновления удаляются из публикуемых журналов; приватные данные и сырой профиль остаются внутри попытки. Блокировка сохраняется до окончания редактирования журналов.

Ошибка модели или квота не переключают ту же попытку на другой аккаунт. Повреждённая, отозванная и неопределённая OAuth-сессия исключается до восстановления; остальные слоты продолжают работу. Для повреждённого слота сначала сохранить причину и подтвердить отсутствие использующих его процессов, затем восстановить **этот слот** штатной командой `login`. Не удалять lock/служебные маркеры для обхода защиты и не копировать старый refresh token. При неопределённом обрыве обновления токенов существующий клиент не гарантирует автоматического восстановления — нужен повторный ручной вход только затронутой сессии.

## Применить инструкции и лимиты через API

Использовать штатные `MULTICA_SERVER_URL`, `MULTICA_TOKEN`, `MULTICA_WORKSPACE_ID`; содержимое токена не записывать в Git, журнал или команду. Приватный deployment содержит UUID прежнего проекта, сквада и трёх ролей. Прежняя подтверждённая PASS receipt используется для обновления инструкций; новый модельный пилот для этого не требуется.

```sh
python3 ~/.local/share/loginom-multica/scripts/configure.py \
  --deployment "$HOME/.config/loginom-multica/deployment.json" \
  --pilot-receipt <проверенная-PASS-receipt> --instructions-only

python3 ~/.local/share/loginom-multica/scripts/concurrency.py \
  --deployment "$HOME/.config/loginom-multica/deployment.json" \
  --parallel 8 --confirm-idle
```

Обновление инструкций меняет только инструкции агентов/сквада и проверяет сохранность остальных настроек. Оно не меняет ref ресурса, лидера, модель, MCP, права или лимиты. Отдельная команда лимитов меняет только `max_concurrent_tasks` на 1/8/8, перечитывает API и сохраняет эти значения в приватном deployment. Ни одна команда не создаёт модельных задач. Роль может иметь восемь активных технических запусков, но модельный пул допускает восемь одновременно; лимит daemon, память и диск остаются дополнительными ограничениями.

## Создать новые LGD/XLSX и продолжать независимые узлы

Старые отменённые карточки не возобновлять. Новые LGD/XLSX сохраняют подтверждённые точки продолжения, существующие PR №38/39 и согласованный Stage 0. Новые UUID получают новую пару аккаунтов Loginom, собственные managed checkout и попытки. В назначении явно записываются узел, этап, исходная ветка и SHA, цель/существующий PR, разрешённые изменения, защищённые файлы, критерии и точка продолжения.

Stage 0 принимается по исследовательским критериям. Нативный импорт, чтение fixture и сборка не подтверждают модельный/продуктовый путь; непройденные циклы остаются NOT_RUN. Общая доставка бинарных файлов или другое изменение общего контракта требует отдельного согласованного назначения. Другие узлы продолжают работу, если подтверждённая техническая зависимость не требует ожидания.

Генератор готовит пары последовательно; исполнитель и reviewer работают по отдельным карточкам независимо. Повтор одного Loginom-аккаунта защищается постоянной account lease, включая браузерные проверки Stage 0 и собственную очистку:

```sh
python3 ~/.local/share/loginom-multica/scripts/account-lease.py \
  --config "$HOME/.config/loginom-multica/cards/<issue>/worker.json" \
  --timeout 7200 -- <foreground-команда-проверки-и-очистки>
```

Полная accept-node приёмка удерживает такую же lease сама. Reviewer использует reviewer.json. Перед передачей роли завершаются технические процессы, публикуются чистый SHA и проверенные доказательства. Неизвестные эффекты сохраняются; попытки не переписываются и не переносятся в новый профиль. Участники исправляют технические проблемы самостоятельно в разрешённом объёме. Владельцу нужен вопрос при изменении критериев/контракта, нехватке доступа либо трёх последовательных попытках без прогресса.

## Проверки и границы

Лёгкая проверка выполняется командой:

```sh
python3 -m unittest discover -s ops/loginom-multica/tests -v
```

Проверяются восемь различных файловых lease и ожидание девятого, наследование блокировки ребёнком при отмене родителя, сохранение фиктивного обновления токена, сроки ожидания и повреждённый слот, запрет ссылок/копий, удаление старых и новых секретов из журналов, сохранность постоянных профилей после очистки попытки, независимость Loginom-аккаунтов, инструкция без сброса настроек и точный service-run idle guard. Проверки используют временные файлы и фиктивные процессы; их PASS не означает восемь настоящих OAuth-обновлений или приёмку узлов.

Установка bundle, целостность CLI, подтверждение восьми ручных авторизаций и совпадение инструкций с API фиксируются отдельно по фактическому выполнению. Восемь реальных циклов с моделью и независимой приёмкой остаются **NOT_RUN**. Слияние и выпуск — отдельная команда владельца. Для возврата к одному запуску требуется свободное окно и `concurrency.py --parallel 1 --confirm-idle`; понижение лимита само по себе не прерывает работающие процессы.
