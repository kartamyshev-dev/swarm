# Два узла одновременно: ручное включение

Подготовлен режим для одного проекта и одного сквада. Генератор остаётся с лимитом 1, Тест-Манки и Ловец получают по 2 запуска. Каждый узел — отдельная карточка, рабочая ветка, native checkout, профиль и пара аккаунтов Loginom. Общая OAuth-авторизация защищена короткой межпроцессной блокировкой при чтении/обновлении; сами модельные запросы выполняются независимо.

Изменения кода сами по себе ничего не запускают. Описанные ниже операции выполняет владелец, когда решит включить режим. Реальную параллельную приёмку эта инструкция не объявляет пройденной. Лимиты 2 у двух ролей позволяют суммарно до четырёх запусков этих ролей; для первого запуска создать только две карточки. Лимит машины, память, нагрузка диска и квота провайдера также ограничивают скорость.

## 1. Подготовить код и окно обслуживания

- Клиентское изменение опубликовано в ветке [`oauth-parallel`](https://github.com/gooddaytoday/loginom-ai-agent/tree/oauth-parallel), коммит `31dfc6412`, от `cross-table`. В свою ветку с подпланом перенести именно этот коммит (`git fetch origin oauth-parallel`, затем `git cherry-pick 31dfc6412`). Если Git сообщает конфликт, сначала разрешить и проверить его; не продолжать подготовку с неполным переносом. Ветка также должна содержать действующие средства CLI-сборки и техническую приёмку своего узла.
- Дождаться завершения текущих запусков; убрать из очереди новые назначения. На время подготовки не отправлять задания, упоминания и сообщения боту, не оставлять запускающие работу расписания. Не останавливать действующую приёмку ради обновления.
- Опубликовать клиентское изменение OAuth и включить его в **каждую ветку с подпланом**, которую будут обрабатывать параллельно. Само обновление ветки общего ресурса этого не делает. Кандидат должен содержать `shared-oauth-v1` в `metadata.capabilities` проверенного `cli-manifest.json`; `bin/loginom-ai-agent-cli --capabilities` также печатает этот признак без модели и Loginom runtime.
- Экспортировать новую обвязку из зафиксированного коммита `swarm` с помощью `scripts/package.py`, как описано в [README](README.md#установка-одной-копии-инструментов), и установить её в `~/.local/share/loginom-multica` только в этом окне обслуживания. Сохранить `VERSION.json`; не смешивать новые скрипты со старой ведомостью файлов.

Для следующих команд на Linux runtime нужны существующая авторизация оператора Multica и приватная рабочая копия `deployment.example.json`, например `~/.config/loginom-multica/deployment.json`. Она должна содержать актуальные UUID проекта, сквада и участников. Настройки моделей, MCP, памяти и репозитория не менять. Не помещать PAT в файл Git или историю команд:

```sh
export MULTICA_SERVER_URL=https://mas.kartamyshev.dev
export MULTICA_WORKSPACE_ID=dcf616e7-66eb-470a-9b04-6462f220cf3b
printf 'Multica PAT: '
read -rs MULTICA_TOKEN
export MULTICA_TOKEN
printf '\n'
```

Скрипты подготовки читают штатный `agent-task-snapshot` и отказываются работать, если видят `queued`, `dispatched`, `running`, `waiting_local_directory` или неизвестный незавершённый статус. Проверка API — снимок, а не запрет поступления новых задач: поэтому окно без новых запусков обязательно. Права PAT должны позволять читать всех трёх участников и состояние рабочего пространства.

## 2. Один раз перенести авторизацию

```sh
python3 ~/.local/share/loginom-multica/scripts/prepare-parallel-auth.py \
  --deployment "$HOME/.config/loginom-multica/deployment.json" \
  --confirm-idle
```

Команда переносит существующий `auth.json` в `~/.config/loginom-multica/provider-auth/auth.json`, сохраняет тот же файл блокировки и обновляет ссылки в `operator.json` и существующих `cards/*/{worker,reviewer}.json`. Новые карточки получают этот путь из оператора. Копии refresh token и ссылки на старый файл не создаются. Каталог 0700 содержит только авторизацию, постоянную блокировку, служебные маркеры и приватные временные файлы атомарной записи; административный конфиг туда не входит.

При нестандартном исходном расположении указать абсолютные `--operator`, `--cards` и `--source`. Имя исходного файла — `auth.json`; целевой `provider-auth` создаётся рядом с ним. При наличии чужого каталога, символьной/жёсткой ссылки, неправильных прав или занятой блокировки команда прекращает работу. Она не исправляет права и не удаляет чужие данные автоматически.

Повтор команды безопасен: сохранённый журнал содержит только пути и состояние; после прерывания она завершит тот же перенос. Пока журнал не завершён, launcher не использует затронутую авторизацию. Если в папке остался только временный файл либо одновременно обнаружены два основных файла, команда останавливается для ручной сверки. Не заменять это копированием старого refresh token.

Совместимому CLI launcher подключит весь **выделенный каталог авторизации** в `/run/loginom-auth` и задаст `LOGINOM_AI_AGENT_SHARED_AUTH_DIR`. Профиль и браузер остаются собственными у каждой попытки. При старом клиенте или неподготовленном каталоге сохраняется последовательный режим. Старый клиент держит тот же `auth.json.lock` на всё время работы; удалить эту блокировку для ускорения нельзя. Не смешивать длинные прогоны старого и нового кандидата: у нового CLI ожидание блокировки ограничено, поэтому он может завершиться ошибкой ожидания, пока старый ещё работает. Перед включением двух приёмок обновить обе ветки.

## 3. Включить лимиты, не создавая заданий

```sh
python3 ~/.local/share/loginom-multica/scripts/concurrency.py \
  --deployment "$HOME/.config/loginom-multica/deployment.json" \
  --parallel 2 --confirm-idle
```

Команда меняет только `max_concurrent_tasks`: Генератор — 1, исполнитель и проверяющий — 2, затем проверяет чтением API. Она не меняет модели, MCP, лидера, ресурс проекта, статусы карточек и не создаёт запусков. При очереди отказывается повышать лимит. Значения также сохраняются в локальном deployment-файле; его следует использовать при последующих загрузках инструкций через `configure.py`, иначе конфигурация без явных лимитов применит исходное значение 1.

Обновлённый шаблон `instructions/squad.md` допускает отдельные карточки узлов и берёт лимиты из настроек Multica. Если установленная инструкция ещё требует строго один запуск, загрузить актуальные шаблоны штатным `configure.py` с **существующей проверенной** PASS receipt и текущим ref ресурса, как в README. Это не требует нового пилота только ради загрузки инструкции; ref не менять наугад. Не запускать `configure.py` со старой копией deployment-файла.

## 4. Запустить самостоятельно

Создать две отдельные карточки в прежнем проекте, назначить обе скваду «Обработчики узлов». В каждую записать:

```text
Ветка: <ветка с подпланом и поддержкой shared-oauth-v1>
Узел: <slug или название одного узла>
Обработать по подплану до независимой приёмки.
Для изменений создать отдельную рабочую ветку и PR в указанную ветку.
```

Генератор подготовит каждую карточку по очереди, далее два запуска исполнителя смогут работать одновременно. Приёмка и независимая проверка сохраняют прежние требования к точному SHA, oracle, закрытию пакета, выходу и публикации доказательств. Не запускать два этапа одной карточки под одним аккаунтом Loginom одновременно. Возврат на исправление должен завершить проверку до следующего этапа.

На первом запуске убедиться, что интервалы двух приёмок действительно пересекаются, обе дали полноценные результаты и независимые проверки; отсутствие OAuth-ошибки или один успешный запрос ещё не доказывают параллельную приёмку. Следить за свободной памятью и задержкой диска. Архивы, дополнительные копии клиента, отдельные проекты и сквады для этой схемы не нужны. GC, постоянные аккаунты и серверные пакеты сохраняют прежние правила.

## Ошибки и возврат к одному запуску

Если CLI сообщает о незавершённом обновлении OAuth, сохранить ошибку и остановить новые прогоны. При таймауте обновления сервер мог уже сменить refresh token: автоматическое повторение прежнего токена запрещено. `refresh-pending.json` служит признаком такого состояния; старый клиент тоже не обходит его. В окне без запусков восстановить авторизацию штатным входом **нового CLI** с `LOGINOM_AI_AGENT_SHARED_AUTH_DIR`, после чего проверить её обычным способом. Не публиковать содержимое файлов и не удалять lock/pending-маркеры для обхода проверки.

Чтобы вернуть последовательный режим на уровне Multica, после завершения запусков и очереди выполнить ту же команду с `--parallel 1 --confirm-idle`. Новый формат авторизации оставляется на месте; обратное копирование токенов не требуется. Понижение лимита не прерывает уже работающие процессы — helper потому и требует свободное окно.
