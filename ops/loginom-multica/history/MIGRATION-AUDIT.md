# Перенос в Multica: аудит и упрощение

Статус на 2 октября 2026: аудит выполнен, новая обвязка ещё не реализована и не включена.
Ветка `multica` создана от актуальной `origin/loginom`:
`9b17e7dd947c016395e8e32e439ca775b1cbe780`.
Пока действуют прежние скрипты Paperclip. Их нельзя считать готовыми для Multica.

## Подтверждённые решения владельца

- Использовать штатные рабочие каталоги, сквад, упоминания, комментарии и статусы Multica.
- Последовательность: Генератор → Тест-Манки → Ловец → Done; вопрос, мешающий продолжению, переводит карточку в Blocked.
- Генератор создаёт для каждой карточки новую пару аккаунтов Loginom. Повторный запуск этой карточки использует ту же пару.
- Аккаунты, постоянные приватные конфигурации и серверные пакеты остаются до ручного удаления.
- Хранить **один текущий готовый кандидат каждого агента**, а не два. После публикации и проверки доказательств и перехода в Done удалить готовые кандидаты этой карточки.
- Архив и его `.sha256` нужны для релиза. Промежуточная сборка обходится без них; манифест и проверка целостности остаются.
- Старые данные и инфраструктуру Swarm не изменять. Merge и релиз выполняются отдельным решением владельца.

## Что показал аудит

### Сбои связаны с несколькими слоями

В последних 100 запусках Paperclip, прочитанных через API, было 46 успешных, 49 отменённых и 5 неуспешных.
Отмену, например при переназначении задачи, нельзя автоматически считать аварией.
Два последних `adapter_failed` содержат ошибку обратного импорта Git bundle через SSH.
Три `configuration_incomplete` связаны с базовым SHA, который не разрешился после fetch.
Эти ошибки сами по себе не доказывают переполнение диска; точная причина отказа Git fetch не установлена.

Есть отдельные признаки тяжёлых задержек диска. В операторских материалах за 1 октября зафиксированы
ожидания `fsync` до 43,748 секунды, а в сохранённом материале проверки C — превышение срока
durable admission в 15 секунд. Общая причина задержек и стабильность хранилища не подтверждены.
Код `packages/loginom-runtime/client/lib/execution-journal.mjs` действительно синхронизирует каждую запись.
Его гарантии нельзя отменять при переносе обвязки: журнал используется для фиксации действий клиента.

На машине Paperclip во время текущей проверки было свободно 131 307 094 016 байт (122,3 GiB),
использовано 68% файловой системы; inode заняты на 22%.
Односекундный интервал `iostat` показал 3,5% занятости диска. Этот короткий замер без приёмки
не доказывает отсутствие повторных задержек под нагрузкой.

### Где копируются данные

`build-candidate.sh` был приспособлен к SSH-синхронизации Paperclip: зависимости вынесены в постоянную
сборочную копию слота, чтобы не переносить примерно 2,3 GB `node_modules` при каждом запуске агента.
Это обход особенностей Paperclip, а не обязательное условие сборки Loginom AI Agent.
В `loginom-swarm/loginom-ops/HISTORY.md` также описаны повреждение относительных ссылок при копировании,
унаследованный рабочий каталог ревьюера, отказ загрузки вложений и цикл повторных пробуждений при 403.
Эти механизмы маршрутизации и восстановления не переносим в Multica.

`build-cli.ts` уже строит во временном каталоге, проверяет манифест и публикует готовый клиент.
Дополнительная внешняя сборочная копия, перенос dirty diff и копирование untracked-файлов здесь излишни.
Для релиза дополнительно создаются архив, его контрольная сумма и распакованная копия для проверки.
`stage-resources.ts` копирует Node и браузеры и устанавливает зависимости runtime-клиента.
Отключение архива убирает архивирование и проверочную распаковку, но не сам готовый клиент и его ресурсы.

Во всех четырёх старых слотах обнаружены:

| Данные | Количество / объём |
| --- | --- |
| Каталоги кандидатов | 38 |
| Архивы кандидатов | 35 / 14 339 380 544 байта (13,35 GiB) |
| Записи в каталогах попыток | 361; это не число успешных приёмок |
| Слот B, полный `du` | 10 492 506 112 байт (9,77 GiB) |
| Слот B, попытки | 3 575 427 072 байта (3,33 GiB) |
| Слот B, сборочная копия | 3 788 095 488 байт (3,53 GiB) |
| Слот B, кандидаты вместе с архивами | 2 946 035 712 байт (2,74 GiB) |

Полное перечисление A/C/R не уложилось в установленный предел 35 секунд на каталог.
Общий размер этих слотов не заявляется. Дополнительные длительные обходы не выполнялись.

Очиститель Paperclip сохраняет исходники и доказательства; слоты A/B/C защищены политикой оператора.
Он удаляет только разрешённый, чистый и подтверждённый хешами payload и не удаляет архивы кандидатов.
Перед таким удалением читает содержимое файлов повторно. Это дорого для нагруженного диска и плохо подходит
для временных сборок, которыми целиком управляет наш скрипт.
Таймер и service сейчас неактивны: согласно последней операторской записи, их **намеренно остановили**
при диагностике I/O. В рамках этого аудита они не запускались, политика не изменялась, данные не удалялись.

### Кеш и размер зависимостей

[Bun использует hardlink на Linux](https://bun.sh/docs/pm/global-cache).
Одинаковые зависимости могут делить физические блоки со штатным кешем; нельзя суммировать размеры
независимых `du` и считать результат уникально занятым местом без проверки hardlink.
В прочитанных образцах `typescript/package.json` было 1 ссылка в A/B и 2 в C;
кеш Bun и слоты находятся на одном устройстве. Полное использование hardlink этим не доказано.
На runtime Multica нужно проверить фактические inode/число ссылок нескольких пакетов.
Свой кеш зависимостей, symlink всей сборки и общее изменяемое хранилище кандидатов не добавляем.

## Упрощённая реализация

**Для обработки узлов нужен только standalone CLI под Linux x64.** Установлено по коду:
`build-candidate.sh` уже вызывает `build-cli.ts`, который передаёт
`--standalone --single --skip-install` в `packages/agent/script/build.ts`.
На Linux x64 это выбирает одну сборку и отключает сборку встроенного Web UI.
Desktop/Electron и отдельные Windows/macOS-артефакты этим путём не собираются.
Повторное объявление «собирать только CLI» само по себе не убирает нынешние лишние записи.

Реальное дополнительное сокращение — установка только зависимостей сборки/проверки CLI.
Сейчас wrapper выполняет `bun install` для всего monorepo. Объявленное замыкание workspace-зависимостей
`packages/agent` и `packages/loginom-host`, включая их devDependencies, содержит 17 из 40 workspace.
Из него исключены Desktop, Web app, Console, Storybook, сайт и другие самостоятельные приложения.
`packages/loginom-runtime/client` отдельно устанавливается через закреплённый npm lockfile с `--omit=dev`;
runtime нельзя потерять при выборе Bun workspace. Нужные `script`, `core`, `schema`, SDK и другие
транзитивные пакеты остаются. Корневые зависимости, не объявленные в собственных пакетах, требуют проверки.

В прочитанном источнике браузеров `cli-0.1.16` находятся `chromium-1243`,
`chromium_headless_shell-1243` и `ffmpeg-1011`. `stage-resources.ts` копирует весь этот каталог.
Манифест указывает обычный `chromium-1243/chrome-linux64/chrome`, а `loginBrowser` передаёт
его как явный `executablePath`. Поэтому нужно проверить возможность копировать только этот Chromium
для приёмки узлов. Исключение headless shell и FFmpeg допускается после проверки полного CLI/MCP-пути
и отсутствия потребности в видеозаписи; одна проверка `loginBrowser` этого не доказывает.
Релизный набор ресурсов при этом сохраняется.

[Bun поддерживает выборочные установки workspace](https://bun.sh/docs/pm/workspaces).
Точный набор фильтров, поведение исключения root и совместимость с закреплённым Bun 1.3.14
нужно проверить реальной Linux-сборкой и целевыми тестами. Сокращение числа workspace не является
доказательством конкретной экономии гигабайтов. Не нужно создавать второй репозиторий или новый lockfile.

1. Собирать непосредственно из рабочего checkout Multica. Установка зависимостей — штатный Bun с frozen lockfile
   и проверенным выбором только CLI workspace и необходимых транзитивных пакетов.
   Не создавать `build/repo`, дополнительный Git clone, синхронизацию dirty diff и отдельный механизм Git-кеша.
   Multica уже предоставляет checkout и [кеш Git](https://github.com/multica-ai/multica/blob/v0.6.1/server/internal/daemon/repocache/cache.go).
2. Использовать существующую временную сборку и проверку манифеста `build-cli.ts`, добавив `--no-archive`.
   Повторно использовать текущий кандидат только при совпадении проверенной идентичности исходников и входов сборки.
   Одного `HEAD` недостаточно для dirty-дерева. После изменения кода нужен новый кандидат.
3. Одна файловая блокировка на `.multica-node` сериализует сборку, приёмку, диагностику и очистку.
   Лимит одного запуска агента остаётся. Не нужны отдельные аренды каждого кандидата, сортировка истории
   по времени и универсальный реестр процессов. Блокировка и подтверждение завершения дочерних процессов обязательны.
4. Новая сборка временно сосуществует с текущей. При неуспехе сохранить прежний кандидат.
   После успешной публикации заменить текущий и удалить прежний, когда он свободен.
5. Один Linux launcher обслуживает CLI, cold-check и разрешённое восстановление Loginom-сессий.
   Повторяющиеся шаблоны bwrap/Xvfb/Openbox объединяются. Новые таймеры, сервисы и слоты не добавляются.
6. Для попытки создавать новый профиль с правильным каналом CLI. После остановки процессов удалять его,
   временные конфигурации и промежуточные файлы. Не менять канал долгоживущего общего профиля и не делать
   резервные копии всего браузерного профиля.
7. Сохранить `result.json`, идентичность исходников и сборки, независимые ожидания, проверенные журналы
   и необходимые доказательства. Не загружать целый клиент, браузеры, зависимости или сырые секретные журналы.
   Финальные материалы публиковать штатными вложениями Multica и проверять сохранённое содержимое.
8. Финальный шаг должен очистить кандидаты **обоих участников той же карточки** после Done.
   Очистка только каталога Ловца не удовлетворяет этому требованию. Путь исполнителя берётся из
   приватной конфигурации карточки; проверяются runtime, issue/agent в маркере владельца, границы
   `.multica-node`, отсутствие внешних ссылок и занятых процессов. Незнакомый/занятый каталог сохраняется
   с диагностикой; очистка не пишет благодарностей и не запускает цикл упоминаний.
9. Весь рабочий каталог удаляет штатный GC Multica. Собственный helper его не удаляет.
   Фактические параметры и журнал daemon на нужном runtime остаются условием включения процесса.

Рекомендуемая структура не содержит второй копии исходников:

```text
<checkout Multica>/
  node_modules/                  штатные зависимости Bun
  .multica-node/
    candidates/<идентичность>/    один опубликованный клиент
    staging/                     только временные файлы сборки
    attempts/<попытка>/
      evidence/                  итоговые материалы
      tmp/                       временный профиль и конфигурации
```

Браузер и Node остаются в проверяемом payload. Общее подключаемое хранилище ресурсов потребовало бы
новых правил версионирования и владения; пока оно не нужно. Сначала измерить результат удаления
архива, повторного копирования checkout и лишних профилей.

## Сохранённые критерии и ограничения

Независимая проверка точного SHA, CLI с моделью `openai/gpt-6-sol`, предел 7200 секунд,
cold-check, проверка чисел/типов и подтверждённое закрытие пакета/выход сохраняются.
Убийство процесса не считается успешным закрытием Loginom-сессии.
Подготовка аккаунтов фиксирует пару до выполнения создания и проверяет неоднозначный исход
вместо слепого повторного создания. Исполнитель не получает административные реквизиты.

Код [GC Multica v0.6.1](https://github.com/multica-ai/multica/blob/v0.6.1/server/internal/daemon/gc.go)
и его defaults прочитаны. API сейчас показывает `Codex (swarm)` online, CLI 0.6.1.
Однако связь доступной машины Paperclip с этой машиной Multica и фактические GC env/logs
не подтверждены. Сроки 24 часа/интервал 2 часа — значения исходников, не установленный срок очистки runtime.
Зависимости checkout, кеш Bun/Git и опубликованные вложения не входят в лимит одного кандидата.
Аккаунты и серверные пакеты продолжат накапливаться по явно выбранной ручной политике.

## Следующий этап и проверка

- Реализовать небольшую общую обвязку, режим без архива, выборочную установку CLI-зависимостей,
  приёмку с `--config` и настройку пары аккаунтов.
- Проверить, что Linux CLI включает нужные host/runtime/Node/Chromium, не создаёт Desktop/Web/Windows/macOS
  артефакты и собирается/проходит целевые проверки после выборочной установки с Bun 1.3.14.
- Проверить весь путь запуска браузера и оставить только необходимые browser-ресурсы для промежуточного Linux CLI;
  не объявлять второй Chromium/FFmpeg лишними только по имени каталога.
- Проверить замену одного кандидата, сохранение рабочего кандидата при сбое, остановку дочерних процессов,
  отказ очистки чужого/неизвестного/занятого каталога и внешней ссылки.
- Проверить повторную обработку карточки без дубликатов аккаунтов и без лишней сборки неизменённых исходников.
- Проверить потерю соединения при загрузке доказательств: локальные материалы сохраняются, Done не выставляется.
- Проверить реальное удаление кандидатов исполнителя и Ловца после Done без дополнительных обсуждений.
- Выполнить реальную приёмку Кросс-таблицы и независимую проверку того же SHA. Отдельно измерить время,
  физическое место и задержки I/O на нужном runtime.
- После успеха опубликовать ветку и переключить ресурс/инструкции через API Multica. При неуспехе ресурс остаётся `loginom`.

Черновой helper на 337 строк с дополнительным clone, переносом patch/untracked и реестром аренд
удалён до публикации. Изменение `build-cli.ts` и замена `build-candidate.sh`, зависевшая от этого helper,
отменены; режим без архива будет внесён и проверен отдельно. Сборки и live-приёмка в этом аудите не запускались.
