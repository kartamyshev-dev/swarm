## Что делает Multica и чего не доказывает этот механизм

Multica создаёт отдельный `CODEX_HOME` задачи, копирует конфигурацию и подключает `auth.json` ссылкой к общему native хранилищу. Backend запускает отдельный `codex app-server --listen stdio://`. Lock в `codex_home.go:433–460` относится к GC/session store, а не к OAuth. Runtime profile позволяет выбрать executable/аргументы поддержанного протокола; он не добавляет блокировку вокруг refresh отдельно запущенного Loginom CLI.

В Codex 0.159.3 `AuthManager.refresh_lock` — локальный Tokio semaphore. Guarded reload подхватывает уже сохранённую новую авторизацию, но два процесса ещё могут одновременно прочесть прежнюю. Файловое хранилище использует truncate/write/flush, без общей OS-блокировки и atomic rename. Это следует из [локального semaphore](https://github.com/openai/codex/blob/01fc69f4026735edfdf6789820549727a4867b11/codex-rs/login/src/auth/manager.rs#L2042-L2062) и [guarded reload](https://github.com/openai/codex/blob/01fc69f4026735edfdf6789820549727a4867b11/codex-rs/login/src/auth/manager.rs#L2487-L2520) и [storage.rs](https://github.com/openai/codex/blob/01fc69f4026735edfdf6789820549727a4867b11/codex-rs/login/src/auth/storage.rs#L183-L227). В сравниваемых stable/alpha/main такая межпроцессная защита также не найдена; обновление версии само по себе её не создаёт.

Риск относится к общей файловой managed ChatGPT OAuth-сессии. Служебный native run затем подтвердил read-only metadata: codex login status → usingChatGPT, exit 0; auth.json имеет тип symlink. Исходный вывод команды не сохранялся; содержимое файла, credentials и сетевая ротация не исследовались. Это не причинное доказательство старых сбоев LGD/XLSX. CI/CD guide отдельно предупреждает против использования одного auth.json в конкурентных заданиях. Наличие online runtime и лимита 20 не доказывает устойчивость OAuth восьми процессов.

Для host, который действительно владеет обновлением токенов, Codex имеет experimental `chatgptAuthTokens`: host передаёт access token/account ID, а на 401 получает запрос обновления с таймаутом 10 секунд. Это возможная основа отдельного native-брокера, но не применённая настройка Multica: нужен совместимый host adapter и квалификация [external_auth.rs](https://github.com/openai/codex/blob/01fc69f4026735edfdf6789820549727a4867b11/codex-rs/app-server/src/external_auth.rs#L18-L81). Multica уже передаёт experimentalApi=true (`server/pkg/agent/codex.go:1511`), но метода account/chatgptAuthTokens/refresh в backend нет; неизвестный запрос попадает в unsupported app-server request (`:2939`). Штатным переключателем API нынешний symlink в такой брокер не превращается.

## Подготовленный shared-oauth-v1

В `31dfc6412` подтверждены: постоянный inode flock, ограничение ожидания 60 секунд; перечитывание токенов и проверка срока внутри lock; HTTP refresh до 30 секунд; временный файл, fsync, rename и fsync каталога; модельный запрос после освобождения lock. Общим должен быть **каталог**, подключённый целиком: отдельный file bind сохранит прежний inode после atomic rename. Desktop и обычные профили без opt-in идут прежним путём.

Найденные условия перед включением:

1. **Неопределённый refresh нельзя подтверждать обычным Auth.set.** `shared.ts:169–172` снимает pending после любого изменения того же провайдера. Проверка Bun 1.3.14 на фактическом модуле подтвердила обход: неоднозначный fake exchange оставил pending; повтор правильно отказал; mutate с тем же прежним OAuth payload удалил pending; следующий refresh снова вызвал exchange с прежним refresh (`attempts=2`, `replayedSameRefresh=true`). Сеть и настоящие credentials не использовались; временный каталог удалён. Требуется идентификатор refresh-транзакции и подтверждение именно её сохранённого результата. Generic set не должен разрешать recovery; новый проверенный login и logout — отдельные явные переходы.
2. **Участники старой версии должны получать отказ.** `shared_auth.py:73–76` сейчас разрешает serial fallback в общем каталоге без capability. Старый клиент не записывает pending перед удалённым refresh: его смерть после ротации оставляет устаревший файл без признака неопределённости. Общий flock не устраняет этот crash-сценарий. Для каталога v1 обязательны совпадающие capability executable/manifest и отказ без скрытого fallback.
3. **Отмена должна охватывать всё ожидание.** Первоначальный `getAuth()` в plugin ещё не получает signal модельного запроса; ожидание может продолжаться до 60 секунд. Ожидание lock должно отменяться общим signal/deadline. Уже отправленная refresh-транзакция должна ограниченно завершить сохранение или оставить durable uncertainty; после отмены модель не отправляется. `Request.signal` также следует учитывать. Удалённый refresh и локальный fsync не являются одной транзакцией — при неопределённом исходе потребуется повторный вход.
4. **Capability должен соответствовать артефакту.** Кандидат объявляет linux/x64, но FFI открывает glibc `libc.so.6`; общее build script имеет и musl targets. Для текущего Ubuntu/glibc требуется реальная проверка полного executable и манифеста. Неподдержанный artifact должен получать отказ.

5. **Личность выбранной авторизации должна быть закреплена.** В `codex.ts:402` новый accountId принимается без сравнения с прежним; SharedAuth проверяет только его тип, chatgpt_user_id не учитывается. На попытку нужны ожидаемые user ID, account/workspace ID и поколение сессии. Чтение и результат refresh сверяются с ними; случайный login/Auth.set другим пользователем не должен менять субъект следующего запроса. При несовпадении — отказ dispatch и определённый recovery/quarantine переход, сохраняющий уже полученный результат ротации. Это обнаруженный пробел контракта, не доказанный инцидент.

Начальное чтение, вход/выход и refresh должны соблюдать один протокол блокировки и сохранения. Общий каталог и постоянный lock нельзя заменять во время работы. Нельзя направлять old CLI, Desktop или обходной auth writer к этому каталогу.

## Обвязка для восьми внутренних прогонов

Нужны явные взаимоисключающие режимы: shared OAuth одного аккаунта и pool восьми разных аккаунтов. Stage 0 не содержит модельной авторизации. Сейчас pool отвергает каталог с shared marker; достижимого self-deadlock в этом пути не найдено. Если снять этот guard и сохранить длинный pool lease, CLI будет ждать собственного удерживаемого flock. Shared mode должен отвергать inherited OAuth lease и использовать только короткую клиентскую refresh-блокировку.

Loginom identity lease, artifact lease и отдельные профили каждой попытки сохраняются. Лимиты worker=8/reviewer=8 допускают суммарно 16 задач, поэтому для ровно восьми внутренних модельных прогонов нужен **общий семафор из восьми execution leases без токенов**. Девятый ждёт с deadline/отменой; FD наследуются потомками. Slot остаётся занят до остановки собственных процессов и sealing доказательств. Это не восемь OAuth-профилей.

Для очистки журналов недостаточно токенов до/после попытки или чтения текущего shared auth: другой процесс может уже заменить использованную пару. Нужен приватный ledger конкретной попытки со всеми значениями, которые CLI реально прочитал/получил/использовал; записывать перед выдачей авторизации в запрос и после ответа refresh. После остановки собственных процессов OPS очищает материалы по ledger, фиксирует завершённость и SHA; publisher сверяет seal/digests и секреты Loginom, не перечитывая живой общий auth. Недостающий ledger или неподтверждённое редактирование запрещает публикацию. Это дополнительная часть интеграции, отсутствующая в подготовленном commit.

Миграция/Login/logout требуют подтверждённого окна обслуживания. Предварительно проверяются все operator/workspace/issue/role/agent bindings; Stage 0 сохраняется байт-в-байт. Исправления этих Stage 0 guards уже внесены в OPS; общая авторизация не активируется. Выбор текущей авторизации slot1 не является доказательством её приёма провайдером после второго входа тем же пользователем.

## Проверки и границы принятия

Сначала реальные отдельные тестовые процессы и локальный fake provider: восемь параллельных streams и один refresh; девятый execution lease ждёт; отмена ожидающего/работающего процесса; одинаковый lock inode через два directory binds; смерть на границах pending/ответ/rename/fsync; отсутствие stale-token replay и generic-set recovery; сохранение других provider записей; ротации во время чужих streams; очистка всех использованных секретов; запрет old/musl/inconsistent capability; сохранность Stage 0 и CLI inventory. Затем полная установленная Linux/glibc сборка с независимыми profiles, Host и браузерами. Исторические source tests кандидата не заменяют эти проверки.

Реальный refresh, восемь реальных модельных циклов и независимая продуктовая приёмка остаются **NOT_RUN**. Одна OAuth-сессия — общий ресурс: отзыв, quota или неопределённая ротация могут остановить все восемь потоков; нельзя переключать аккаунт/повторять сомнительную транзакцию автоматически.

Рекомендация: подготовить отдельный исправленный opt-in контракт Loginom CLI и интеграцию OPS; существующий `31dfc6412` не включать без перечисленных исправлений. Native авторизацию Codex Multica квалифицировать отдельно; при общей file-managed OAuth нужен механизм единственного refresh writer, например проверенный external-token host adapter. Новая SIWC регистрация/endpoint не подменяет действующий legacy Loginom flow: это отдельная миграция, а не исправление блокировки.

Текущий этап ограничен исследованием и уже согласованными OPS исправлениями Stage 0. Изменения клиента, native broker, автоматический запуск LGD/XLSX, merge/release не выполнены.
