# Telegram для Multica

Один бот подключён штатно к Генератору тасок. Только backend Multica получает
Telegram updates и выполняет привязку пользователя. Отдельный небольшой
`telegram-notifier` читает API Multica раз в 30 секунд и вызывает только
Telegram `sendMessage`; webhook и второй `getUpdates` не нужны.

Уведомления относятся к скваду «Обработчики узлов» и его трём агентам:

- переход карточки в Blocked;
- настоящее упоминание владельца участником сквада;
- ошибка запуска, попавшая в штатный Inbox владельца;
- ответ человека после уведомления о вопросе;
- снятие Blocked с переходом в In Progress, Review или Done.

После первого непустого комментария человека бот сообщает «Ответ в карточке
получен». Пока статус Blocked, это не означает, что агент уже принял ответ.
Переход карточки в работу, Review или Done подтверждается сообщением
«Блокировка снята» с текущим статусом. Если ответ и снятие блокировки замечены
в одном опросе, приходит одно сообщение о снятии блокировки. Комментарии агентов
ответом человека не считаются; содержание ответа в Telegram не копируется.

До следующего ответа человека повторные упоминания владельца в той же карточке
не порождают новые вопросы в Telegram. После ответа следующий вопрос снова
может уведомить владельца. Старый вопрос, на который ответили до доставки,
пропускается. Прочтение Inbox само по себе вопрос не закрывает.

На вопрос нужно отвечать **в карточке Multica** по кнопке из уведомления.
Обычная переписка с ботом является отдельным чатом Генератора и автоматически
не становится ответом в карточке. Для вопроса владельцу Генератор использует
настоящее `mention://member/<UUID владельца>`; вопросы между агентами остаются
с упоминаниями агентов.

## Установка

Код и шаблоны находятся здесь, установленная копия —
`/opt/multica/telegram-notifier` на сервере Multica. Требуются Python 3.13 и
только его стандартная библиотека. Образ закрепляется по digest; портов,
зависимостей npm, Docker socket, доступа к БД и файлов агентов у сервиса нет.

`MULTICA_TELEGRAM_SECRET_KEY` в backend — постоянный случайный 32-byte ключ
в base64. Токен бота регистрируется штатным API Multica у Генератора, сохраняется
в БД зашифрованным. Для отправки уведомлений его отдельная копия, выделенный PAT
владельца и private chat ID находятся только в `credentials.json` (0600).
PAT имеет права владельца; код сервиса использует только GET к Multica. У
установленной версии нет отдельного PAT scope для чтения Inbox.

Сначала пользователь нажимает Start в личном чате бота и привязывает аккаунт
через ссылку Multica. Оператор проверяет, что channel_user_binding принадлежит
нужному владельцу и этой установке бота; его Telegram user ID является адресом
личного чата. Без этой проверки получателя не задавать. Другим членам workspace
бот доступен после их собственной привязки, но уведомления владельца туда не
пересылаются.

Заполнить `config.json` по шаблону, задать `enabled_at` текущим Unix time,
добавить сервис из `compose.fragment.yaml` к существующему Compose. Приватные
файлы и каталог state должны принадлежать uid/gid 10001. Сервис не требует
изменений API Multica или настроек runtime.

## Хранение и пределы

SQLite содержит только ID событий, ID карточек, времена, признаки доставки и последние статусы, без копий
комментариев, логов и сборок. Записи событий хранятся 30 дней. Записи меняются
при событиях; heartbeat хранится в tmpfs. Docker logs ограничены двумя файлами
по 1 MiB. После перезапуска уже отправленные уведомления повторно не отправляются.
История до `enabled_at` не рассылается, существующие статусы становятся baseline.

Если Telegram/API недоступен, ожидающие события остаются в SQLite и повторяются
при следующем опросе. При неоднозначном сетевом сбое после принятия сообщения
Telegram возможен повтор: sendMessage не имеет idempotency key. Уже завершённые
карточки и устранённые блокировки пропускаются. Переход в Blocked и выход из
него между двумя опросами может остаться без уведомления; для постоянных
блокировок обычная задержка до 30 секунд плюс время запросов.

Вопросы и ошибки зависят от штатного Inbox владельца: его подписок и notification
preferences. Сервис не отмечает уведомления прочитанными и не меняет карточки.
Проверить subscriptions при отсутствии уведомлений. Полные сообщения могут
содержать чувствительные сведения; в Telegram отправляется ограниченный текст
с маскировкой известных форматов токенов и полей паролей, без вложений.

## Проверки

`python3 -m unittest discover -s ops/multica-telegram -p 'test_*.py' -v`

На сервере: `docker compose ps telegram-notifier`, healthcheck и реальная
доставка тестового уведомления. Блокировку проверять отдельной служебной
карточкой: сначала создать без назначения, затем назначить скваду и поставить
Blocked с `suppress_run=true`. Подтвердить ноль task-runs и запись delivered
в очереди. Не упоминать агентов. После теста снять назначение и поставить
Cancelled с `suppress_run=true`; реальные задачи не изменять. Вопрос проверяется
unit-тестом отбора настоящего упоминания владельца; проверка реального вопроса
агента требует отдельного разрешённого запуска.
